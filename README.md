# Supplier Entity Resolution and Data Quality POC

## Overview

This project solves a supplier entity-resolution and data-quality problem for a procurement digitalization proof of concept.

The client provided a raw Excel file containing supplier names and up to five candidate company matches per input row, generated by an entity-resolution engine. The goal is to select the best real-world company match for each supplier, leave weak matches unresolved when appropriate, and identify data-quality issues in the selected company records.

The solution is implemented as a Jupyter notebook using a medallion architecture:

```text
Raw input file
→ Rule-based entity resolution and QC
→ First-pass resolved/QC output
→ Generated labels
→ Predictive model
→ ML-scored resolved/QC output
```

The project is designed to be transparent, explainable, and suitable for a data analyst case-study submission.

---

## Business Problem

The procurement team is unable to analyze supplier spend effectively because the supplier master data contains messy, duplicate, incomplete, and outdated company records.

This creates problems for:

- supplier spend visibility
- category management
- cost-saving analysis
- supplier risk review
- future sustainability analysis
- supplier master data governance

The objective of this POC is to demonstrate a repeatable workflow for cleaning and resolving supplier entities.

---

## Project Objectives

The project addresses two core tasks.

### 1. Entity Resolution

For each input supplier, the notebook evaluates up to five candidate matches and selects the most plausible real-world company.

Each supplier is classified as one of the following:

- `Auto-match`
- `Review match`
- `Unmatched / research required`

The matching process uses company-name similarity, domain evidence, geography, candidate rank, and score separation between the top candidates.

### 2. Data Analysis and Quality Control

After selecting the best candidate, the notebook checks the selected entity attributes for inconsistencies and missing values.

Examples of QC checks include:

- missing website
- country mismatch
- weak candidate separation
- missing revenue
- missing employee count
- no reliable match
- possible parent/subsidiary ambiguity

The output includes a QC issue backlog and a stewardship review queue.

## Architecture

The notebook follows a Bronze, Silver, and Gold medallion architecture.

### Bronze Layer

The Bronze layer preserves and profiles the raw input data.

It performs:

- raw Excel ingestion
- ingestion metadata creation
- row and column profiling
- missing-value profiling
- candidate count analysis
- raw data persistence

Bronze answers the question:

> What data did we receive?

### Silver Layer

The Silver layer cleans, standardizes, and engineers analytical features.

It performs:

- company-name normalization
- legal suffix removal
- website and domain normalization
- country, city, and postcode standardization
- fuzzy name-similarity scoring
- token-overlap scoring
- rare-token weighting
- domain-alignment checks
- geography checks
- candidate-context feature creation
- rule-based scoring
- candidate ranking
- generated label creation
- predictive model training
- model validation
- overfitting checks

Silver answers the question:

> How do we compare and evaluate candidate matches?

### Gold Layer

The Gold layer creates business-ready outputs.

It performs:

- final best-match selection
- confidence banding
- match-decision assignment
- QC issue generation
- review queue prioritization
- business metric creation
- Excel export

Gold answers the question:

> What should the business do with the results?

## Workflow

The notebook follows this sequence:

```text
1. Load the raw Excel candidate file
2. Profile the raw data
3. Normalize supplier and candidate names
4. Engineer name, domain, geography, and enrichment features
5. Score each candidate using transparent rule-based logic
6. Select the first-pass best match per supplier
7. Generate QC issues and review actions
8. Export the rule-based resolved/QC workbook
9. Convert the rule-based selections into training labels
10. Train a predictive model
11. Validate the model using grouped train/test logic
12. Apply overfitting controls
13. Score candidates with the predictive model
14. Export the ML-scored resolved/QC workbook
```

---

## Key Design Choice

The raw client file does not contain ground-truth labels.

Because of that, the notebook does not immediately train a supervised model. Instead, it first creates a transparent rule-based resolution output.

That first-pass output is then converted into generated labels:

```text
selected candidate = 1
non-selected candidate = 0
unmatched candidate = 0
```

These generated labels are used to demonstrate how the workflow could evolve into a predictive model once reviewed labels are available.

This avoids pretending that supervised training data exists when it does not.

---

## Rule-Based Matching Logic

The rule-based scorer uses a weighted combination of features such as:

- normalized name similarity
- partial name similarity
- token-sort similarity
- token-set similarity
- legal and commercial name variant similarity
- weighted rare-token overlap
- same-country flag
- same-city flag
- same-postcode flag
- website availability
- domain alignment with supplier name
- original engine candidate rank

The score is used to rank candidates within each input supplier group.

The notebook then applies conservative business rules to avoid over-automating risky cases.

For example, a candidate may be downgraded from `Auto-match` to `Review match` when:

- the candidate country does not match the input country
- the selected candidate has no website
- the score gap between the first and second candidate is small
- the candidate appears to be a possible hard negative

---

## Predictive Modeling

After the first-pass resolution output is created, the notebook trains a supervised model using the generated labels.

The predictive model estimates:

```text
Probability that a candidate is the correct match for the input supplier
```

The model uses features from the Silver layer, including:

- fuzzy name-matching features
- token-overlap features
- rare-token features
- domain features
- geography features
- enrichment completeness features
- candidate ranking features
- baseline rule-score features

The default model is Logistic Regression because it is simple, explainable, and suitable for a POC.

The model output is a calibrated match probability, which is used to select and classify final matches.

---

## Overfitting Controls

The notebook includes several safeguards against overfitting:

- grouped train/test split by `input_row_key`
- GroupKFold cross-validation
- regularization tuning for Logistic Regression
- baseline-feature ablation
- learning curve analysis
- train vs validation metric comparison

The grouped validation approach prevents candidate rows for the same supplier from appearing in both training and validation sets.

This is important because each input supplier can have multiple candidate rows.

## Recommended Interpretation

The rule-based output should be treated as the primary POC deliverable.

The ML-scored output should be treated as a demonstration of future automation potential, because the model is trained from generated first-pass labels rather than independently reviewed human labels.

For a production implementation, the next step would be to have data stewards review high-priority cases and use those reviewed labels to retrain and validate the model.

---

## Limitations

This project has several important limitations:

- The raw file does not contain true ground-truth labels.
- The first predictive model is trained on labels generated by the rule-based process.
- Some matches may require external research to validate the real-world company.
- Parent/subsidiary relationships are difficult to resolve using only the provided candidate attributes.
- Website and country mismatches are useful risk signals but do not always prove that a match is wrong.
- The model should not be considered production-ready until validated against human-reviewed labels.
